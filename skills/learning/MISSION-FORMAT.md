# MISSION.md 格式

`MISSION.md` 位于工作区根目录。它记录用户学习这个主题的**原因**。每一个教学决策（接下来教什么、呈现哪些资源、设计什么练习）都应能回溯到这份文档。

## 模板

```md
# 使命：{主题}

## 为什么
{1–3 句话。用户在追求的具体现实目标。掌握了这个技能，他们的生活或工作会有什么改变？避免"为了理解 X"这类抽象表述；追问底层结果。}

## 成功的样子
- {一件具体的、可观察的、用户将能做到的事}
- {另一件具体的事}
- {……}

## 约束
- {时间、预算、既有承诺、学习偏好——任何框定方法的东西}

## 范围之外
- {用户明确表示现在不想追的相邻主题，保护最近发展区}
```

## 规则

- **一个工作区一个使命。** 用户想学两个不相关的东西，那就是两个工作区。
- **具体压过抽象。** "十月底跑完半马"好过"变得更健康"。"给团队交付一个 Rust CLI"好过"学 Rust"。
- **对含糊其辞要追问。** 如果用户说不清为什么学，先访谈他们再动笔（至多 2-3 轮）。仍说不清就如实写"动机暂缺"并动笔——动机空缺本身是有用信息，不要以"坏的使命比没有使命更糟"为由不建文件。
- **现实变了就修订。** 使命会变。当用户的目标移动了，更新这份文件：别让一份过期的使命继续给后续会话导航。
- **保持简短。** 如果 `MISSION.md` 超过了一屏，它就不再是罗盘，而是变成了计划。
